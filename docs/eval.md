## Fix applied during this eval (Finding 1: `sources` field, logged during Task 12)

`_validate_sources` in `comparison.py` only stripped fabricated text that looked like a URL but didn't match a real one — non-URL garbage (e.g. `"Highway MPG: 19 (Dataset)"`) passed through untouched. Fixed: non-URL sources are now only accepted if they're essentially just the provenance word itself (`"dataset"`, `"the dataset"`, `"car dataset"`, `"local dataset"`) — anything else non-URL is dropped. `SYSTEM_PROMPT` also reinforced to ask for exactly the word "dataset". Verified with 7 unit cases (including the exact original bug example) before the eval run, then confirmed clean across every question in this eval that reached `human_review` (#3, #8, #9, #10).

## Fix applied during this eval (Finding 3: `gas` substring match, question 5)

`validate_requirements`'s `_matches_real_value` treated any substring match against a real category as valid, so `"gas"` (substring of the real category `"natural gas"`) was kept as the filter value even though the buyer meant fuel-efficient gasoline generally. Fixed with a small `AMBIGUOUS_FUEL_TOKENS` denylist (`{"gas"}` for now) checked before the substring test — demotes to `must_haves` instead. Legitimate substring matches (`"SUV"` → `"4dr SUV"`, `"diesel"` → `"diesel"`) confirmed unaffected.

## Finding 2 (not a code bug — operational/infra observation)

Several turns during this eval took far longer than the ~4 minute baseline established in Task 12 (one took roughly half an hour). This coincided with an earlier batch of 4 concurrent long-running requests hitting the single self-hosted Ollama instance simultaneously — confirmed via `ollama api/ps` that the model runs with `size_vram: 0` (CPU inference, not GPU), so concurrent requests genuinely compete for the same CPU cycles rather than running in parallel, and the instance appears to take a while to recover to baseline latency afterward. Task 13's concurrent-request lock correctly prevented this from corrupting state or racing (confirmed: retries during the slow period consistently got `"busy"`, never a duplicate invoke) — but the raw latency itself is a real operational risk worth knowing about, especially for Task 16's video recording: avoid firing concurrent requests against this Ollama instance, and expect a single turn to occasionally take much longer than 4 minutes under real conditions.

## Known limitations, deliberately left deferred (re-confirmed still the right call)

- **Cross-car URL misattribution** (Task 8): `_validate_sources` checks a URL exists anywhere in the flat `web_results` list, not that it was returned for that specific car's query. Real URL, possibly wrong car. Not re-exercised conclusively in this eval (question 10 had no web results to test against). Fixing properly requires `search_web_node` to return per-candidate results instead of a flat list — a real data-flow change, not attempted this close to the deadline.
- **Free-text qualitative claims aren't fully validated** (observed in question 10): pros/cons prose can carry a vague, unfalsifiable-sounding claim (e.g. "above average quality and reliability as per consumer reviews") that isn't a specific number or URL, so no current validator catches it. Lower severity than the numeric/citation fabrication classes already fixed (Tasks 7, 8, this eval) — noted for awareness, not fixed.
